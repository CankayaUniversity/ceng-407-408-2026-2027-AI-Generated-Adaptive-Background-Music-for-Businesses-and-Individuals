# AGENTS.md

Guide for every agent (and human) writing code in this repository. Read this first, then the
`AGENTS.md` of the app you are working in (`apps/web/AGENTS.md`, `apps/api/AGENTS.md`).

## Project
An uploaded image or a periodic webcam snapshot is turned into a mood, the mood previews matching tracks from the user's library, and after approval the system generates a varied playlist and streams it back.

### Pipeline

1. **Extract mood.** FastAPI sends the image to an OpenAI-compatible LLM endpoint chosen by the operator and
   asks for structured output: three axes in `[-1, 1]`, namely `valence` (sad to happy), `texture`
   (acoustic to electronic) and `energy` (calm to energetic), plus a short summary and tags.
2. **Preview matches.** While the user tunes sliders, a plain SQL Euclidean-distance query in
   PostgreSQL returns the top 3 library tracks. No vector extension is needed for 3 dimensions.
3. **Plan prompts.** After approval the same LLM writes 5 (default) to 25 varied song prompts.
   The maximum depends on the user's tier. Prompts follow the ElevenLabs Music prompting guides.
4. **Generate.** A worker runs the generation jobs asynchronously against ElevenLabs Music (in
   batches where the API allows) and stores the MP3s in SeaweedFS (S3 API).
5. **Adapt.** Periodic webcam adaptation regenerates without asking for approval. The user can
   still open the sliders and tune manually at any time.

Rules for the layout:

- Apps never import each other's source. `web` talks to `api` only over HTTP. Shared contracts
  are the API's OpenAPI schema. Generate TypeScript types from it; do not hand-copy them.
- Each app owns its own dependency manifest and lockfile (`apps/web/package-lock.json`,
  `apps/api/uv.lock`). There are no root-level npm workspaces.
- Nothing is hard-coded, and everything is configured by the admin in the web app: providers,
  models, API keys, limits and plans. It is stored in Postgres with secrets encrypted. Only
  the `postgres_password` and `app_encryption_keys` Docker secrets live outside, in `secrets/`
  (created by `infra/init-secrets.sh`). There is no `.env` file. Details
  are in `apps/api/AGENTS.md` and ADR 0003.
- Generated files carry a "generated" header. Regenerate them; never hand-edit them.

### Running the web app

```bash
cd apps/web
npm install
npm run dev            # http://localhost:3000
npm run typecheck      # next typegen + tsc
npm run lint
npm run build
npx astryx doctor --built .   # must report 0 failures before a UI change is delivered
```

To change the theme, edit `src/themes/frost/frostTheme.ts`, then run `npm run theme:build`. To
change the tint itself, edit `scripts/generate-frost-palette.mjs`, then run
`npm run theme:palette && npm run theme:build`.

Fonts are self-hosted through `src/themes/frost/frost.fonts.css` (`@font-face` pointing at
`src/themes/frost/fonts/`, which also holds the licence). The UI font is Host Grotesk (OFL). Never
load fonts through a remote CSS `@import` or a Google Fonts `<link>`: Next.js drops remote
`@import`, and self-hosting keeps visitors' browsers from contacting Google. Astryx doctor only
counts fonts declared in `<slug>.fonts.css`, so keep them there rather than in `next/font`. To
change the font, swap the files and `@font-face` rules, update `typography` in `frostTheme.ts`,
then run `npm run theme:build`.

## Source control: GitHub Flow

The strategy is **GitHub Flow**, chosen by the project team.

- `main` is always releasable and protected. Nobody pushes to it directly, agents included.
- Every change goes on a short-lived branch cut from an up-to-date `main`:
  - `feat/<scope>-<short-desc>`: new behaviour, e.g. `feat/api-mood-extraction`
  - `fix/<scope>-<short-desc>`: bug fixes
  - `docs/...`, `chore/...`, `refactor/...`, `test/...`, `ci/...`
  - `<scope>` is `web`, `api`, `infra`, `docs` or `repo`.
  - Tool-named prefixes such as `codex/` or `claude/` are not allowed.
- Push early and open a pull request against `main`. A PR must have:
  - a description of what and why, with the issue linked if there is one;
  - green CI;
  - at least one approving review from a human team member.
  The reviewer merges only after the project operator approves.
- Merge with **squash merge**. The squash title follows Conventional Commits. Delete the branch
  after merging.
- Keep PRs small and single-purpose. Split cross-app work (`web` + `api`) into separate PRs
  when each can land on its own; land the API side first.
- Rebase your own unpushed branch on `main` as often as you like. Pushed, shared history is not
  rewritten. Force-pushes to shared branches, deleting remote branches and skipping hooks all
  need the operator's approval first.
- Releases (course milestones and demos) are tags on `main`: `vMAJOR.MINOR.PATCH` with release
  notes. Tag only when the operator asks.

### Commits

- Use Conventional Commits: `type(scope): summary`, written in the imperative mood. For example,
  `feat(api): extract mood axes from image via LLM`.
- Make each commit one coherent step that builds and passes tests on its own. Keep refactors,
  formatting and behaviour changes in separate commits.
- Use the summary for what the commit does and the body for why.
- Commit under the human operator's git identity, never as an AI author. Name the agent role in
  a trailer:

  ```text
  feat(web): add mood slider preview

  Agent-Role: coder
  ```

- No AI tool (Claude, Codex or any other) may appear as an author, committer or contributor.
  Never add `Co-Authored-By` or other AI attribution trailers or signatures to commits or PRs.
- Never commit secrets, the `secrets/` folder, `.env` files, build output, `node_modules`, `.next`, virtualenvs or
  generated media. Keep `.gitignore` current.

### Recommended GitHub settings (operator applies; agents never change them)

- Branch protection on `main`: require a PR, 1 approval, passing status checks and a linear
  history; disallow force-push and deletion.
- Allow squash merge only; enable "automatically delete head branches".

## Working agreements for agents

- Read the app-level `AGENTS.md` before touching an app. In `apps/web` that means following the
  Astryx rules (no raw `<div>`, tokens instead of hex or px, start from templates). Never edit
  inside the `nextjs-agent-rules` or `ASTRYX` marker blocks, because the tools regenerate them.
- When unsure about scope, a library choice or a strategy, ask the operator rather than guessing.
- Leave the tree clean. Before you open a PR, lint, typecheck, run the tests and build the app
  you changed.
